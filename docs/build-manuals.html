Read the right version

Yocto publishes one manual set per release and one for the development branch. You are on OE-Core master — your LAYERSERIES_COMPAT names blacksail, the master codename — so the dev manuals describe the classes and variables you actually have. The unversioned site tracks the latest release (currently the wrynose LTS): close, not identical. If you pin to a release later, switch manuals the same day.

How the stack works — from the card to the browser

One workstation, one GPU, one control plane. Read this bottom-up once and every line the coder prints will have a place to land.

Browser / apps
symoneural.com pages (static HTML generated by Python, read /api/status and one WebSocket) · later: iPhone/Android/TV clients over the same API.
Edge
Cloudflare DNS proxy (the 522 in your tab is Cloudflare saying the origin is unreachable) → Caddy :443 — TLS and static files only; every other path is reverse-proxied. Rule from your Caddyfile: FastAPI does all the routing.
Gateway
symon-gateway :8000 (Rust, axum) — forwards /api verbatim, relays /api/ws as a real WebSocket, validates chat payloads before anything can take the GPU lock. No auth, no payments, no TLS.
Control plane
= DispatchOS
FastAPI :8800 (backend/api.py) — the unit registry (build_status()), the GPU queue and lock, the live bus, receipts, per-surface tokens, rackpower. This is what Symoneural-API exists to build.
Services
Engines the control plane starts under the lock: llama-server :8081 (resident), sd-cli (per request), ffmpeg/gstreamer → HLS, Stratum V2 pool + translator, kawpowminer, whisper-cli, the trainer, ComfyUI :8188. Each is a process, most are one recipe.
Runtimes
The Symoneural-* folders — pinned source trees, curated recipes, and the built output in prod/{bin,lib}. A runtime is a buildable library set; a rack unit is a running service. One runtime serves several units: LLM serves Chat, Coder and the Studio agent.
Build system
Symoneural-Build: OE-Core + BitBake at pinned master SHAs turn each source tree into cross-compiled packages, with a licence manifest and SPDX SBOM per recipe. The acquisition control plane guarantees every binary traces to a commit and a licence file.
Hardware
RTX 5070 Ti — 70 SMs, 15.92 GiB GDDR7, 752 GB/s measured (896 vendor), 48 MB L2, 300 W · PCIe Gen 3 ×8 host-capped: 6.94 GB/s host→device measured, though the card does Gen 5 · i9-10900KF · 94 GB RAM · driver 610.57.04 / CUDA 13.3 · NVMe for weights.

Why the design is the way it is

VRAM is the budget. Chat at 64K context holds ~8.2 GiB; FLUX schnell holds ~7 GB with T5 pushed to the CPU. They do not both fit in 15.92 GiB, so the machine runs one GPU tenant per job. That single fact produces the lock, the queue, the rack states, and the "busy / queued / ready" vocabulary on the site.

PCIe Gen 3 ×8 makes weight swaps cost seconds, not milliseconds — loading is bandwidth-bound at ~7 GB/s. The 94 GB of RAM is the second tier: weights stay hot in page cache and move to the card when a surface wins the lock. This is also why llama-server stays resident between chat turns while sd-cli runs per request and evicts it.

CPU units never touch the lock. RavenCalc (SymPy), Coder, Project, DispatchOS itself, Voice ASR (whisper.cpp built GGML_CUDA=OFF, 284 MiB RSS) all run beside the GPU, never on it. That is what lets them stay ready while a render holds the card.

The lock, exactly

Two layers. In-process, GpuQueue is an asyncio.Lock plus a Semaphore(24); hold(surface) announces queued → acquired → released on the bus. Cross-process, scripts/gpu-governor.sh is a mkdir mutex at run/gpu.lock.d with a holder file "<surface> <pid>" and a run/resident record of who has weights loaded. Acquire spins on mkdir up to 300 s, breaks stale holders (kill -0 fails), evicts the previous resident per surface (chat → stop llama-server; image/sigil → pkill sd-cli; comfy → stop ComfyUI; train → refuses; miner → stop), then drains until nvidia-smi reports under 1,500 MiB or 60 s. Release refuses a mismatched holder.

Three rules govern precedence and they are worth keeping verbatim: the lock is held per job, never per process lifetime; train is never evicted; miner yields to everything.

That is the August implementation, described so the mechanism is understood. The estate's DispatchOS is free to rebuild it — as a proper service rather than a shell script — but the constraints it enforces are physics, not preference: one GPU tenant per job, explicit precedence, drain before hand-over.

One request, end to end

  1. Browser opens symoneural.com/chat; Cloudflare resolves and proxies to your origin.
  2. Caddy terminates TLS; /api/* is handed to symon-gateway with flush_interval -1 so tokens are never buffered.
  3. symon-gateway checks the payload size and token estimate, appends its hop to X-Forwarded-For, forwards to FastAPI.
  4. FastAPI routes POST /api/chat, calls GpuQueue.hold("chat"); the governor acquires the mutex, evicts a resident image job if one holds the card, drains VRAM.
  5. If llama-server is not resident it is started: -m Qwen2.5-7B-Instruct-Q4_K_M.gguf -ngl 99 -c 65536 -np 2, plus the speculative 0.5B draft and --lora symoneural-lora.gguf; health is polled on :8081 for up to 120 s.
  6. Tokens stream back as SSE through gateway and Caddy to the page; the WebSocket bus emits rack and patch frames so every open page updates without polling.
  7. The job ends, the lock is released, the rack row returns to ready, and a receipt is recorded.

Models, adapters, training — how they connect

Weights live on disk (backend/models/, ~40 GB) as GGUF for llama.cpp and stable-diffusion.cpp and as safetensors for anything torch touches. Training is QLoRA: PEFT loads the base in NF4, trains a rank-16 adapter (alpha 32, seven target modules), and the adapter is converted with convert_lora_to_gguf.py --outtype f16 so llama-server applies it at serve time with --lora. That is the whole SymonChat personality loop: corpus → adapter → GGUF → --lora. Studio is the training bay; Reinforce is its SFT / DPO / GRPO preset system; Exp is a plugin container, not training at all.

What the estate adds to this picture

The August deployment ran on Debian system packages and per-app virtualenvs. The estate replaces every one of those binaries with a build from a pinned source tree through OE-Core — same processes, same ports, same lock — so that llama-server, sd-cli, the trainer's torch and the site's HLS player are all yours, traceable, and rebuildable on this box.

Runtime to production — the procedure

The same ten steps take every runtime from a pinned tree to a unit on the rack. The table after it holds what differs per runtime. Steps are ordered because each depends on the last.

  1. Source at the intended revision. The control plane already proves this: source-lock.json matches source-manifest.json, submodules at recorded commits, tree clean under git status --ignored.
  2. Recipe curated. No recipetool stubs beside an inherit; LICENSE and LIC_FILES_CHKSUM read from the real files (all of them, never narrowed); out-of-tree build so B != S; no class that writes into ${S}.
  3. Build. From the runtime's build/devtool-master with BB_NUMBER_THREADS = "10" and PARALLEL_MAKE = "-j 12": bitbake symoneural-<component>. One bitbake per build directory; never edit a recipe while it runs.

  5. Licence and vulnerability evidence. bitbake <recipe> -c create_recipe_sbom for the SPDX document; cve-check. Both are free; both go in the receipts.
  6. Package and install. do_package emits ipk/rpm per PACKAGE_CLASSES; install into the runtime's prod/{bin,lib}, or generate an SDK/sysroot for the Python runtimes so the interpreter and its extensions come from the same build.
  7. Service unit. Start from ops/symoneural-api.service: User=google, ExecStartPre releases stale governor locks, ExecStopPost kills engine children, MemoryMax, the moderate hardening set, journal logging. One unit per long-running service; per-job engines are spawned by the API under the governor, never as units.
  8. Register the unit. Add it to DispatchOS (today a Unit(...) in build_status(); move this to a registry file), give it a bus, a page generator in tools/build_*.py, and a token switch in /etc/symoneural/api.env.
  9. Health. The rack row reads ready from /api/status; the engine's own health endpoint answers; the Playwright suite passes in a real browser.
  10. Expose and commit. Caddy handle → symon-gateway → API; sudo scripts/deploy.sh --prune for the static site; commit explicit paths, never git add ..

The five new runtimes — what each is, what exists, what to acquire

These are named in the estate and on the rack but never acquired. The August code already contains most of their logic; the acquisitions below are the upstream sources that logic depends on, so they can be built here like everything else. Decisions are stated with a recommended answer; the final word is yours.

Symoneural-UI

What it is. The website and, later, the surface every native client mirrors. In August it was 18 Python generators emitting static HTML, one hand-written CSS file and a 22 KB console.js — framework-free, with hls.js and Swagger UI the only vendored JavaScript. That is history, not a constraint.

Recommendation, independent of what August did. Choose the lightest UI that can render the rack live: a generated static site over the WebSocket bus. It needs no Node toolchain to build, has no dependency closure to audit, and deploys with a copy — which matters in an estate whose whole argument is provenance. If you want a richer application shell later, that is the moment Next.js (MIT, pinned to a release tag, never canary) or a Tauri wrapper enters, after nodejs lands via meta-openembedded. Acquire now: nothing. The UI runtime is your generators, CSS, JS, brand assets and browser tests.

Symoneural-Gateway

What it is. Three things share the name and should become one runtime: the HTTP front door (symon-gateway, Rust, your code), the TLS/static edge (Caddy), and workspace licensing (TRON USDT TRC-20: SymoneuralLicence.sol, tronpy CLI, settlement → Ed25519 entitlements — compiled and tested, never deployed, no wallet, no key).

Acquire: Caddy — github.com/caddyserver/caddy (Apache-2.0, Go; OE-Core has Go) · cloudflared — github.com/cloudflare/cloudflared (Apache-2.0) if you take the tunnel route below · tronpy — github.com/andelf/tronpy (MIT) · coincurve — github.com/ofek/coincurve (MIT OR Apache-2.0). symon-gateway's crates arrive through its Cargo.lock as a tracked closure; note from the earlier audit that axum, tokio, hyper, tower are MIT-only while serde, reqwest, rustls are dual-licensed. Also finally build ops/middleware/limiter.wasm — it never was, so the gateway runs in native fallback.

Decision. Cloudflare Tunnel (no open ports, origin certificate) versus DNS-only with Caddy's own ACME as in August. Recommended: tunnel — the DNS is already proxied, and a workstation with no inbound ports is the right posture. Caddy stays behind it for static files and compression.

Symoneural-Diffuse

What it is. The Image and Sigils units: FLUX.1-schnell at q4_k through stable-diffusion.cpp, T5 on the CPU, 4 steps. Studio's renders went through ComfyUI instead.

Acquire: stable-diffusion.cpp — github.com/leejet/stable-diffusion.cpp (MIT) at an exact tag, with the provenance flag that its ggml submodule is leejet/ggml, a personal fork, not ggml-org/ggml · diffusers — github.com/huggingface/diffusers (Apache-2.0) for Studio renders and image LoRA training · rembg — github.com/danielgatis/rembg (MIT) · whisper.cpp — github.com/ggml-org/whisper.cpp (MIT), both currently in virtualenvs. Weights go in the models register, not the estate.

Decision. Keep ComfyUI as an isolated GPL-3 process, or retire it for diffusers. Recommended: retire it. It carried a second torch (2.13 + cu130) and a GPL frontend package; diffusers on Common's torch gives Studio one substrate and removes a licence flag.

Symoneural-Studio

What it is. The training bay. QLoRA via PEFT (NF4, rank 16, paged_adamw_8bit, bf16, loss masked to the assistant turn), TRL for DPO and GRPO on a branch, presets, a VRAM planner, and the 27B path with its four documented traps (vision tower on CPU, embed gather shim, streamed cross-entropy). Plus the agent loop with 26 tools and an MCP server.

Acquire: peft — github.com/huggingface/peft (Apache-2.0) · trl — github.com/huggingface/trl (Apache-2.0) · bitsandbytes — github.com/bitsandbytes-foundation/bitsandbytes (MIT; CUDA kernels must build for sm_120) · datasets — github.com/huggingface/datasets (Apache-2.0). The MCP server moves from fastmcp to the python-sdk already in CLI.

Decision. Which torch. Common holds 2.14; the August trainer ran 2.11 + cu128; FreeToken demands >=2.11,<2.12. Recommended: Common's torch is the torch for the estate — Studio and Diffuse build on it; Adaptive-Fabric either follows it or pins its own and stays a separate runtime. Do not run two.

Symoneural-Tune

What it is. The GPU itself as a managed device: the telemetry the rack footer shows (VRAM, power, temperature, PCIe link), power limits, persistence mode, and your own CUDA kernel work — the NVRTC engine in apps/reinforce/symoneural/ (12 __global__ kernels, sm_120 targets, 112 tests) and the 34-sample CUDA curriculum with "on this box" results.

Acquire: nvidia-ml-py (BSD-3, NVIDIA's NVML binding; the PyPI sdist is the source) · CuPy — github.com/cupy/cupy (MIT) · cuda-python — github.com/NVIDIA/cuda-python — characterise its licence on acquisition, do not assume. The CUDA Toolkit and driver are proprietary: they enter as BINARY, REFERENCE acquisitions under NVIDIA's EULA and the estate records that honestly — Tune can never be fully source-built, and the register should say so.

Decision. Telemetry plus power limits through NVML, or fan curves and clocks too. Recommended: telemetry and power limits now (root via a small privileged helper); fan and clock control needs X11 through libXNVCtrl (MIT, inside the GPL nvidia-settings tree) — defer until there is a display server to justify it.

Web, which you left off the list

workerd and workers-sdk are already acquired. With Cloudflare in front of the domain they have a real job: static and API caching at the edge, and the tunnel's counterpart. Recommended: fold Web into Gateway as its edge half rather than keeping a twelfth runtime for two packages.

Edge, domain, security

How symoneural.com reached the box in August. DNS pointed straight at it; Caddy did ACME TLS on :80/:443, served /var/www/symoneural, and proxied /api /v1 /swagger-ui /api-docs to symon-gateway :8000 and /docs /openapi.json plus the section pages to FastAPI :8800. X-Forwarded-For handling is deliberate: Caddy replaces untrusted inbound headers with the real peer, the gateway appends its hop, and the API keys its rate limiter on the first entry.

What changed. The 522 in your browser tab is a Cloudflare status — the domain is now proxied through Cloudflare and Cloudflare could not reach the origin. Two consequences: Caddy's HTTP-01 ACME challenge will not complete behind a proxy, and every visitor's first hop is Cloudflare, so the rate-limiter chain in the Caddyfile note ("if a proxy is ever put in front of Caddy, this block must change") is now live.

  1. Choose the origin posture. Tunnel (cloudflared, outbound only, no inbound ports, Cloudflare terminates public TLS, origin certificate between Cloudflare and Caddy) — recommended for a workstation. Or DNS-only "grey cloud" and Caddy's ACME as before.
  2. Fix the forwarded chain. With Cloudflare in front, Caddy needs trusted_proxies naming Cloudflare's ranges and should read CF-Connecting-IP; otherwise every visitor shares one rate-limit bucket.
  3. Add customer authentication before public exposure. /api/chat, /api/image and /api/status had no auth; the per-surface X-Sym-Token switches protect operator surfaces only. Accounts (scrypt, SQLite) exist and are routed but "not open yet".
  4. Keep licensing off the app store path. TRON settlement happens on the website; clients only read an entitlement (see Native apps).

Native apps — iPhone, Android, Fire TV, Windows, Mac

The box is the product; every client is thin. Nothing in the rack moves to a phone — what moves is the surface. Your routes for Voice, Sigils and Project were already designed for this: stable JSON, header tokens, no session assumptions. Do it in this order and each step is shippable.

  1. Progressive Web App first, this week. A manifest.json, icons from brand/, and a service worker for the shell make the existing site installable on iPhone, Android, Windows, Mac and the Fire TV browser with zero new code. It also forces the API to be the only interface — the discipline everything below relies on.
  2. Publish the contract. FastAPI already emits /openapi.json. Freeze a versioned copy in the repo; every native client is generated from it, never hand-written.
  3. iPhone, iPad, Mac — one SwiftUI codebase. Generate the client with Swift OpenAPI Generator (Apple, Apache-2.0). Streaming: SSE tokens via URLSession.bytes(for:), the rack bus via URLSessionWebSocketTask. Sign in with Apple maps to an entitlement token from your accounts service. Push through APNs when a queued job completes. SwiftUI multiplatform covers macOS natively; Catalyst is not needed.
  4. App Store rules that touch this product. No on-device mining (the Miner screen is control and telemetry only — that is fine). Digital goods must use In-App Purchase, and an app may not link out to an external crypto payment to unlock features: keep TRON licensing on symoneural.com and have the app read the entitlement it already has. Background audio for Remix needs the audio background mode and a real player.
  5. Android and Fire TV. Kotlin + Jetpack Compose, client generated with OpenAPI Generator (kotlin). Fire OS is Android: the same app, with Compose for TV / Leanback and Media3 ExoPlayer for HLS — Streamer and Live are the units that map most naturally to a television. Ship through the Amazon Appstore or sideload for your own devices.
  6. Windows. The PWA is the honest first answer. If a shell is wanted, Tauri (MIT OR Apache-2.0) wraps the same site with a native window and a small footprint; Electron is the heavier alternative.
  7. Offline and on-device modes, later. Apple silicon can run small models locally — llama.cpp with Metal, MLX (MIT), or Core ML conversions — for a degraded mode when the box is unreachable. Keep the 5070 Ti as the place heavy work happens; on-device is a fallback, not a second product.
One rule for all of them

A native client never talks to an engine port. It talks to the same /api the website uses, through the same gateway, under the same lock. That is what keeps thirteen units and five platforms one system instead of six.

Customer runtimes — a DispatchOS per customer

"Have one built" means a customer gets their own SyMoNeuRaL: a dedicated DispatchOS instance with the units they bought, their own tokens and accounts, their own receipts and page — presented to them as theirs. The sources are already in the estate; what is new is making DispatchOS instantiable.

  • One template, many instances. symoneural-dispatch@.service is a systemd template; symoneural-dispatch@donnie reads /etc/symoneural/tenants/donnie/ (tenant.json, units.json, api.env, accounts.env) and binds its own loopback port. The binaries are the estate's, shared; only configuration differs.
  • One card, one governor. Tenants do not get their own GPU lock. Every tenant's GPU units queue on the single estate governor, so two customers' jobs never collide on VRAM and the rack states stay truthful across tenants.
  • Their view, not yours. A tenant page shows only that tenant's units and receipts, at <name>.symoneural.com or symoneural.com/<name> through Caddy and the gateway. Operator surfaces (Studio, Exp, Rack power, Miner) never appear in a customer's rack.
  • Units decide readiness. A tenant made of CPU and NET units — RavenCalc, Project, Coder, Streamer — is presentable as soon as Phase 11-T lands. A tenant that includes Chat waits for Phase 12; Image for Phase 14. What the customer asked for sets the date.
  • Secrets per tenant. symoneural-secrets setup --tenant donnie generates that tenant's tokens and accounts secret under its own directory; nothing is shared between customers.

Onboarding — request, verify, approve

A customer never receives a password and you never hand one out. The front door is a single field.

  1. The customer enters an email on the tenant's /account page. The API records a pending request (email, tenant, IP, time) and sends a verification link to that address — nothing reaches you yet, so a stranger typing addresses cannot fill your inbox.
  2. The customer clicks the link (single-use, 15-minute expiry, token hashed at rest). The request becomes verified.
  3. You receive one email at symonsayadmin@symoneural.com: who, which tenant, when, from where — with two signed, single-use links, Approve and Deny, valid for seven days. The same decision is available from the box: symoneural-cli accounts approve <id>.
  4. Approve creates the account inside that tenant's accounts store and emails the customer a sign-in link. Sign-in stays passwordless (a magic link per session); an API key can be issued to the account later for native clients. Deny closes the request; nothing is sent unless you choose to.

Outbound mail goes through Zoho Mail, where symoneural.com's mail already lives: smtp.zoho.com:587 (STARTTLS) authenticated as your mailbox with a Zoho app password, never the login password. Three Zoho facts govern it: SMTP needs a paid plan (Mail Lite or above — the free plan has no SMTP access); the From address must be the authenticated mailbox or one of its aliases, so noreply@symoneural.com is an alias to add before switching MAIL_FROM to it; and DKIM is enabled per domain in the Zoho admin console (Email Authentication → DKIM), which hands you one TXT record for Cloudflare DNS — SPF is already in place if inbound mail works. The API sends a few messages a day, far under Zoho's limits; if volume ever grows, Zoho's ZeptoMail is the transactional tier and uses the same mail.env shape.

The org invite link is also omitted on purpose: it was exposed in a screenshot and still needs rotating, so reprinting it would widen an exposure that is already open.
